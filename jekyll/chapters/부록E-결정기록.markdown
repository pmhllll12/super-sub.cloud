# 부록 E. 결정 기록

프로젝트를 진행하며 **실제로 채택한 결정**, 그렇게 정한 **이유**, 함께 검토했으나
**채택하지 않은 대안과 그 이유**, 그리고 **언제 정해졌는지**를 한자리에 모은다.

> **정본은 개발 로그(`/devlog/`)와 미결 항목(`/pending/`)이다.** 이 페이지는 사람이
> 훑어보도록 추린 것이라, 각 항목의 상세한 근거·수치·검증 과정은 링크한 원문에 있다.
> 결정이 바뀌면 원문을 고치고 이 표를 따라 갱신한다.

**읽는 법.** 「대안 / 기각」이 있는 항목은 다른 길을 실제로 재보고 접었다는 뜻이다.
「되돌림」·「보류」로 표시된 것도 결정이다 — 왜 그 길로 가지 않는지가 기록으로 남아야
같은 조사를 반복하지 않는다.

## 1. 분석·AI 판정

### 1) 측정과 판단의 분리
- **채택** — 영상을 언어 모델에 직접 넣어 점수를 매기게 하지 않는다. 관절 각도·각속도
  같은 수치는 결정론적 포즈 추정 코드가 산출하고, 언어 모델은 그 수치를 채점 기준과
  대조해 **판정만** 한다. 총점 계산은 애플리케이션 코드가 한다.
- **이유** — 언어 모델은 픽셀에서 각도를 측정할 수 없다. 측정하지 않은 값을 그럴듯하게
  지어내고 같은 영상에서 다른 점수가 나온다. 근거를 댈 수 없는 점수는 실력 검증
  산출물이 될 수 없다. 부록 D가 `analysis_metric_value`(측정)와 `analysis_report`(생성물)를
  별도 테이블로 나눈 것과 같은 구조다.

### 2) 포즈 추정 스택 — OpenCV 디코딩 + RT-DETR + ViTPose (COCO-17)
- **채택** — 프레임 디코딩은 OpenCV, 사람 검출은 RT-DETR, 키포인트는 ViTPose.
- **대안 / 기각** — 설계 초안의 **MediaPipe Pose(33관절)**. 필수 투입자원 목록에
  MediaPipe가 없고 OpenCV·Transformers가 지정돼 있어 실제 환경에서 접었다.

### 3) 판정 모델 — EXAONE 4.0 1.2B (오픈 웨이트, transformers 네이티브, bf16)
- **채택** — 개발 GPU가 RTX 3050 8GB라 8GB에 올라가면서 원격 코드 없이 transformers에
  네이티브 통합된 모델이 4.0 1.2B뿐이었다. 재현성 실측은 3회 반복 표준편차 0.00.
- **대안 / 기각**
  - **상용 API 모델** — 초기 전제였으나 오픈 웨이트로 전환. 이때 "파인튜닝 금지, 루브릭·RAG로 해결"과 "`temperature` 미지정" 두 결론이 뒤집혔다(자체 서빙은 기본값 0.7이라 명시하지 않으면 점수가 요동).
  - **EXAONE 3.5/4.x 32B~33B** — 4비트 양자화로도 19GB 안팎이라 8GB에 적재 불가.
  - **EXAONE 3.5 7.8B** — `trust_remote_code`가 특정 transformers 버전 창에만 맞아, 팀 전원이 재현하는 환경에서 상류 변경에 깨진다.
  - **비전-언어 모델** — 8GB에 불가. 그래서 에이전트는 키프레임 이미지를 보지 못하고, 시선·표정처럼 수치화 못 하는 항목은 루브릭에서 제외했다.
  - **EXAONE Deep(추론 특화)** — 추론 토큰 생성으로 지연이 크고 출력 스키마 문법 강제와 충돌.
  - **4비트 양자화** — 1.2B에서는 역양자화 오버헤드로 적재 6배·생성 2배 느려 손해. 작은 모델은 양자화하지 않는다.
- **비고** — 모델을 바꿔도 루브릭·출력 스키마·파이프라인은 재사용되고 교체 범위는 판정 백엔드 한 곳이다.

### 4) 등급 판정을 언어 모델이 아니라 코드가 내린다
- **채택** — 루브릭이 수치 구간을 선언하고 `Criterion.grade_for()`가 등급을 정한다
  (양끝 포함, 높은 등급 우선). 언어 모델의 몫은 근거 문장 생성만 남기고 스키마에서
  `grade`를 제거해 등급을 뒤집을 경로 자체를 없앴다.
- **대안 / 기각** — 스키마에 대조 추론 필드를 넣어 언어 모델이 등급을 판정하게 하는
  방식. 1.2B가 경계값 비교(141.7 vs 140)를 반복해서 틀렸고, 등급 정의가 이미 수치
  구간이라 판정에 추론이 필요 없었다. 산문 기준("150~170도")의 경계 겹침도 코드로
  내리며 없앴다(경계 29건 검증).

### 5) 출력 스키마 문법 강제 + 필드 순서로 사고 순서 고정

  필드 구성이 판정 정확도를 바꾼다는 실측.

### 6) 산출물은 점수표가 아니라 칭호
- **채택** — 총점·배점표를 화면에서 접고, 항목마다 비유를 하나 잡아 등급에 따라
  굴리는 칭호를 산출물로 한다. 칭호 문구는 UI가 아니라 루브릭 `titles`에 둔다.
- **이유** — 루브릭이 지도자 검수 전이라 점수 자체가 `provisional`이고, 선수에게
  보여줄 것은 무엇이 나아지고 나빠졌는지 읽히는 단어다.

### 7) 루브릭 단위는 (종목, 동작), 동작은 사용자가 선택
- **채택** — 종목 하나가 아니라 (종목, 동작) 쌍마다 루브릭을 둔다. 업로드할 때 사용자가
  (종목, 동작)을 고른다.
- **이유** — 같은 지표가 동작에 따라 반대로 채점된다(임팩트 시 무릎각 176도: 인스텝
  슈팅 1점, 인사이드 패스 0점). 농구는 점프슛과 레이업이 임팩트로 삼는 프레임 자체가
  다르다.
- **대안 / 기각** — 동작 자동 판별. 임팩트를 찾으려면 `impact_limb`·`impact_event`를
  먼저 알아야 하는데 그 둘을 루브릭이 선언하고, 같은 종목의 슛/패스는 각도 분포가
  겹쳐 잘못 고르면 점수가 조용히 틀린다.

### 8) 품질 게이트에서 손목을 필수 관절에서 제외
- **채택** — 사지마다 요구 관절 수를 `GATE_JOINTS`로 명시한다 — 팔은 어깨·팔꿈치 2개,
  다리는 발목까지 3개. 손목은 게이트에서만 빠지고 프레임 단위 유효성 마스크에는 남는다.
- **이유** — 외부 포즈 3,444클립에서 손목 때문에 79%가 탈락했는데, 팔 루브릭이 손목을
  쓰는 곳은 팔꿈치각 하나뿐이었다. 게이트 조정 후 최종 지표 산출률이 야구 21% → 71%,
  농구 11% → 40%로 올랐고 통과 클립의 측정값은 100% 동일.
- **대안 / 기각** — 다리도 같이 면제하는 것. 무릎각이 `joint_angle(엉덩이, 무릎, 발목)`이라
  발목이 빠지면 각도가 NaN이 되고 임팩트조차 못 찾는다(축구 17/17 실패). 체인마다
  잘라도 되는 자리가 다르다.

  신뢰도 값 25만 개를 전수 조사해 0과 0.5 사이 값이 하나도 없음을 확인.

### 10) 분석 대상 selector(A-pose / B-pose) 결정 보류
- **보류** — 영상에 여러 사람이 잡힐 때 누구를 분석할지 정하는 selector를 놓고
  후보 5종을 비교했으나, 마지막 둘(연속성 가점 유무)을 **현재 데이터셋으로는 가릴 수
  없다**. 격리 판독 60건, 부트스트랩 95% 구간이 [0.40, 0.80]로 0.5를 포함.
- **이유** — 유의하게 가리려면 판정 가능 340건이 필요한데 이 데이터셋의 상한이 약 49건.
  질문을 "어느 selector인가"에서 "연속성 가점을 언제 신뢰할 것인가"로 바꾼다(사람
  라벨 없이 측정 가능).

### 28) GPU 인스턴스는 쓸 때만 켠다 + 자동 종료

### 32) 미결 항목을 팀 요청·결정의 공통 입구로
- **채택** — 다른 사람이 판단·조치해야 하는 것은 자기 폴더 문서에만 두지 않고
  `jekyll/pages/pending.markdown`에 한 항목으로 올린다(담당·제기·기한). 요청은
  "이 파일을 고쳐라"가 아니라 **"이 성질을 만족하라"**로, 확인 방법과 하지 말아야 할
  것을 함께 적는다. 받은 요청은 고치기 전에 이미 됐는지 확인하고, 이미 만족하면
  손대지 않는다.
- **이유** — 커밋은 전달이 아니다(사람별 브랜치라 `main` 전에는 `git pull`해도 못
  받는다). 저장소 문서도 진입점에서 가리키지 않으면 안 읽힌다. 문서는 스냅샷이라
  상대가 나중에 읽을 때 이미 다른 방식으로 해결됐을 수 있다.
- **정한 날 / 기록** — 2026-09-01 · 루트 `CLAUDE.md` 「미결 항목」 절 ·

### 33) 미결 항목을 브랜치별 구역제로
- **채택** — 미결 항목을 제기자의 브랜치별 구역(`## jin (정어진)` 등)으로 나누고 각
  항목은 `###`로 둔다. 자기 구역에만 추가하고 번호는 구역 안에서만 센다. 다른 파일에서
  가리킬 때는 번호가 아니라 제목으로 쓴다.
- **이유** — 전부 파일 끝에 붙이면 두 사람이 동시에 올릴 때 매번 충돌한다(2026-09-01에
  실제로 겪고 실험으로 확인). 구역 기준을 담당자가 아니라 제기자로 두는 것은,
  담당자 기준이면 남의 구역에 쓰게 되어 충돌이 되살아나기 때문.
- **대안 / 기각** — 평면 목록 유지. 병합 시 평면으로 되돌리면 다음 사람이 또 파일 끝에
  붙인다. 판별은 `grep -n '^## [0-9]' jekyll/pages/pending.markdown`이 0건인지로 한다.

### 34) 백엔드 미구현을 테이블 수가 아니라 도메인으로 분담
- **채택** — 남은 두 도메인을 통째로 넘긴다: 과금(3테이블) → 백성검, 평가·신뢰(5테이블)

  `tests/conftest.py`, `test_auth_router.py`, `down_revision`)은 정어진이 배선한다.
- **이유** — `app/<컨텍스트>/` 구조를 아키텍처 테스트가 검사하므로 도메인 경계가 곧
  폴더 경계다. 도메인으로 자르면 두 사람의 파일이 안 겹친다. 테이블 수로 균등하게
  자르면 한 도메인이 둘로 쪼개져 같은 폴더를 둘이 만지게 된다. `down_revision`은 자동
  병합이 안 되는 자리(head가 둘이 되면 `alembic upgrade head`가 죽는다).
