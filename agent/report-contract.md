# 분석 리포트가 담는 것 — 읽는 쪽을 위한 지도

**누구를 위한 문서인가.** `POST /analyses` 적재(정어진)와 리포트 조회 경로
(미결 `paik` 7번), 그리고 화면 배선(백성검, `min` 9번 3조각)이 **같은 JSON 을
읽습니다.** 무엇이 어디 있는지 한 장에 둡니다.

**어디에 있나.** `reports/<user_id>/<video_id>/report.json` (S3). 그 자리는
완료 보고에 `report_key` 로 실려 옵니다 — 계산하지 마시고 그 값을 쓰세요
(미결 `paik` 11번).

**적재 입력은 이 파일 하나입니다.** 에이전트는 같은 결과를 두 벌로 만들어
보내지 않습니다 — `POST /analyses` 본문에 `metrics[]` 를 또 싣는 초안 형태는
택하지 않았습니다(미결 `jin` 27번의 권고안에 동의). 트리거를 어디에 둘지는
백엔드 몫이고, 어느 쪽이어도 워커는 DB 접속 정보를 모릅니다.

🔴 **필드 목록의 정본은 `contracts/report_schema.yaml` 입니다** (2026-09-10,
미결 `jin` 27번). 앞서 이 자리에 「정본은 코드」라고 적어 두었던 것을
**정정합니다** — 그러면 스키마가 조용히 바뀔 수 있고, 적재·읽기 경로·화면
셋이 같은 JSON 을 읽으므로 그 변경은 **백엔드 배포 뒤 실서버에서만** 드러납니다.

- **필드가 있는가·없는가** → `contracts/report_schema.yaml`
- **값이 어떻게 만들어지는가** → 코드 (`scripts/analyze_s3.build_report` ·
  `scoring.aggregate`)
- 둘이 어긋나면 **`tests/test_report_contract.py` 가 빨개집니다.** 사람이 어느
  쪽이 맞는지 정하고 **둘을 함께** 고칩니다 (사본을 하나 더 두는 것이 아니라,
  사본이 갈라지는 것을 막는 장치입니다)

## 봉투 모양이 바뀔 때 — `schema_version`

리포트 최상위에 `schema_version` 이 실립니다(지금 **`"1.4"`**). 값은 위 yaml 의
`version` 이고, 테스트가 둘이 같은지 봅니다.

🔴 **앞서 이 자리를 `"1.1"` 이라고 적어 둔 것을 정정합니다** — `title_earned`
(1.2)·`skeleton`(1.3·1.4)이 늘 때 yaml 의 `version` 만 올리고 **이 줄을 안 고쳤습니다.**
받는 쪽은 이 문서를 보고 자기 코드의 기대 버전을 정하므로, 낡은 값이 적혀 있으면
**최신 봉투를 「모르는 버전」으로 거부**할 수 있습니다. 변경 이력의 정본은 yaml
머리말입니다.

| 무슨 변경 | 어떻게 | 받는 쪽이 할 일 |
|---|---|---|
| 필드를 **늘린다** | `1.0` → `1.1` + 미결 항목에 한 줄 | 모르는 키는 무시하면 됩니다 — 적재는 안 깨집니다 |
| 필드를 **빼거나 뜻을 바꾼다** | `1.x` → `2.0` + 미결 항목으로 **미리** 알림 | 그 키를 필수로 읽고 있으면 깨집니다 |

**1.1 이 무엇인가**: `breakdown[]` 에 `view_dependent` 가 늘어(11 → 12필드)
버전을 올렸습니다 (미결 `ho` 37번 처방 (다) · 알림은 `ho` 38번).
🔴 **앞서 필드만 늘리고 버전을 안 올렸던 것을 정정합니다** — 위 표를 이 파일에
적어 두고 스스로 어겼고, 그동안 받는 쪽은 `1.0` 봉투와 12필드 봉투를 **구분할
방법이 없었습니다.** minor 라 적재는 안 깨집니다(major 만 거부 기준).

🔴 **모르는 major 를 만나면 적재를 거부하는 것이 맞습니다.** 반쯤 적재하면
어느 행이 낡은 스키마에서 온 것인지 사후에 구분할 방법이 없습니다.

## 성공 보고에는 **항상** `report_key` 가 실립니다

워커의 완료 보고(`PATCH /internal/analysis-jobs/{id}`)가 `succeeded` 라면
`report_key` 가 함께 있습니다 — 적재는 그 하나만 입력으로 받으면 됩니다.

자리를 못 실은 경우(자리 파일 없음·다른 버킷·두 건이라 모호)는 **`failed` 로
보고합니다.** 키 없는 성공은 **영원히 빈 리포트**라서입니다 — 작업은 끝난 것으로
닫히고 화면은 아무것도 못 찾으며 사용자에게는 재시도할 방법도 안 보입니다.
검사는 `test_worker.py::test_a_success_is_never_reported_without_a_report_key`
(네 가지 경우 전부). 🔴 앞서 워커 주석에 "자리를 못 실어도 성공으로 보고한다"고
적혀 있던 동작을 **정정한 것입니다**.

### `breakdown[]` 항목 필드 — 이 열세 개가 전부입니다

미결 `jin` 27번이 요청한 목록입니다. **테이블 (b)** (`analysis_metric_criterion`)
컬럼을 여기 맞추시면 됩니다. 정본은 `contracts/report_schema.yaml` 의
`breakdown_item` 이고, 검사는 `test_report_contract.py`
(`test_the_breakdown_fields_are_exactly_the_contract`).

| 필드 | 타입 | 적재할 때 |
|---|---|---|
| `criterion_id` | string | 🔴 **종목·동작 안에서만 유일합니다** — 등급 코드는 `grade.{sport}.{motion}.{criterion_id}` (`jin` 23번) |
| `name` | string | 사람이 읽을 항목 이름. 라벨 정본은 `metric_definitions.yaml` 쪽이라 참고용입니다 |
| `grade` | int (0·1·2) | 판정 등급. 숫자 적재는 `grade.*` 코드 행 |
| `weight` | number | **재정규화된** 값(판정된 항목 합 1.0). 루브릭 원값이 아닙니다 |
| `contribution` | number | 이 항목이 총점에 실제로 보탠 점수(0~100 축) |
| `title` | string | 등급별 칭호. 🔴 **모든 등급에 있고 비지 않습니다** — 0·1등급에는 「무너지는 축」·「설익은 축」 같은 **부정적인 문구**가 옵니다. 루브릭이 안 적었으면 항목명이 폴백으로 옵니다 |
| `title_earned` | boolean | **받은 호칭인가** (`paik` 23번). 참인 항목의 `title` 만 「받은 호칭」으로 그리세요. 조건은 **최고 등급(2) + 루브릭이 그 등급의 문구를 실제로 적었을 것**. 🔴 거짓을 **미달 표식으로 그리지 마세요** — 안 그리는 것이 맞습니다(계약 4장) |
| `band` | string | 🔴 **선수 화면에 내지 않습니다** (검수 전, 미결 24번). 파싱하지 마세요 |
| `out_of_band` | string | 비어 있지 않으면 0등급이 **구간 위**에서 왔다는 표시(미결 20번). 개발 확인용 |
| `view_dependent` | string | 등급이 **촬영 방향에 의존하는가**(미결 37번). `""` · `"metric"` · 🔴 `"grade"`. 개발 확인용 — 아래 「화면에 낼 때」 참고 |
| `stat` | number\|null | 레이더 축 값 0~100. 코드는 `stat.{sport}.{motion}.{criterion_id}` (`jin` 25번) |
| `evidence` | string | 항목별 근거 문장 — `paik` 7번의 「특징 문장」. 🔴 **등급 표기가 없습니다**(정규식으로 뽑지 마세요). 🔴 **지표 코드도 없습니다** (2026.09.11~) — 앞서 「측정값 `swing_knee_angle_at_impact`=151.6로…」가 그대로 나가던 것을 고쳤습니다. 🔴 **아직 남은 것**: 루브릭 문구에서 온 **구간 숫자**(「140~165도」)는 문장에 나올 수 있습니다 — 미결 23번이고 지도자 검수에 묶여 있습니다 |
| `metric_ref` | string | 근거로 삼은 지표 코드. 이름·단위는 `metric_definitions.yaml` |

`skipped[]` 항목은 셋입니다 — `criterion_id` · `name` · `weight`(루브릭 원값).

🔴 **`margin` · `confident` 는 이 리포트에 없습니다.** HTTP 데모 경로
(`api.run_pipeline`)만 붙이는 필드라 적재가 필수로 읽으면 실서버에서
`KeyError` 입니다. 필요하시면 미결 항목으로 알려 주세요 — 형제 필드라
싣는 것은 값쌉니다(검사가 지금 「S3 봉투에는 없다」를 고정하고 있습니다).

버리고 있었습니다** — 71%로 겨우 통과한 클립과 여유 있게 통과한 클립을
읽는 쪽이 구분할 수 없었습니다. 그 값을 봉투에 싣습니다.

```json
{ "known": true, "limb": "leg", "side": "auto",
  "swing_side_valid_ratio": 0.94,     // ← 컬럼을 더하실 값 (예시 값입니다)
  "gate_joints": 3, "threshold": 0.7, "min_keypoint_confidence": 0.3 }
```

| | |
|---|---|
| 무엇인가 | **스윙 측 게이트 관절의 유효 프레임 비율** (0~1, 백분율이 아닙니다) |
| 🔴 아닌 것 | **키포인트 신뢰도 평균이 아닙니다.** ViTPose 는 top-down 이라 엉뚱한 박스를 줘도 자신 있게 관절을 냅니다 — 평균이 높은 것이 「잘 잡았다」가 아닙니다. 「**누구를** 쟀는가」는 `subject` 가 답합니다 |
| 하한 | `threshold` 미만이면 **애초에 리포트가 없습니다**(분석이 반려됩니다). 그래서 실린 값은 항상 이 값 이상입니다 |
| `known: false` | 정규화 자체가 안 되는 입력입니다. 그때는 비율이 없습니다 — 🔴 **0.0 으로 채우지 마세요**(「쟀는데 나빴다」로 읽힙니다) |
| 사지별 기준 | `min_keypoint_confidence` 가 다릅니다 — 팔 0.6 · 다리 0.3. 손목이 가장 어려운 관절이라 그렇습니다 |

`features` 의 **형제 블록**입니다 — `timebase`·`subject` 와 같은 자리라
판정 입력이 그대로이고, 기존 평가와의 비교가 끊기지 않습니다.

## `skeleton` — 관절 시계열과 세 순간 (2026-09-15 신설, 미결 `paik` 30번)

비교 화면(「선수와 비교하기」)이 **자세 세 장을 겹쳐 그리는** 자리입니다.
지금 그 화면은 **브라우저에서 관절을 다시 뽑고 있습니다** — 그래서 ⑴ 위쪽
리포트(에이전트 값)와 **다른 계기에서 온 자세**를 겹쳐 놓고 있고 ⑵ 영상 두
편을 매번 훑느라 느립니다. 이 키가 둘을 함께 없앱니다.

```json
"skeleton": {
  "known": true,
  "fps": 15.0,
  "frames": 76,
  "frame_size": [1920, 1080],
  "swing_leg": "right",
  "keypoint_names": ["nose", "left_eye", "...", "right_ankle"],
  "moments": {"before": 41, "impact": 46, "after": 61},
  "moments_seconds": {"before": 2.733, "impact": 3.067, "after": 4.067},
  "joints": [[[0.4821, 0.3915, 0.94], "... 17점"], null, "..."]
}
```

| 키 | 무엇 |
|---|---|
| `joints` | 프레임당 **COCO-17 × `[x, y, confidence]`**. 좌표는 `frame_size` 로 나눈 값입니다 |
| `keypoint_names` | 17개 이름. 🔴 **인덱스의 뜻을 추측하지 마세요** — 자기 상수표를 따로 들면 두 표가 갈려도 아무 데서도 안 터집니다 |
| `moments` | 프레임 번호. `impact` 는 `segment_phases` 가 고른 값 **그대로**입니다 |
| `moments_seconds` | 같은 값을 초로. `target_fps` 로 나누면 20% 어긋나서 함께 냅니다 |
| `swing_leg` | **차는 다리**. `swing_side` 가 `auto` 였으면 이 값이 판별 결과입니다 |
| `direction` | **차는 방향** — 화면 오른쪽이 `1`, 왼쪽이 `-1`. 상체 기울기를 「차는 방향으로」 읽을 때 씁니다 |
| `after_clipped` | `after` 가 **클립을 넘쳐** 물러섰는가. 참이면 「접촉 후」는 진짜 +1초가 아닙니다 |
| `known: false` | 합성 키포인트 경로 등 — `why` 만 있고 나머지 키가 없습니다 |

**세 순간과 방향의 정의** (화면이 정본입니다 — 에이전트가 고른 것이 아닙니다).
🔴 규칙은 `www/src/lib/motion/moments.ts` 와 **같은 것을 옮긴 것**이라 한쪽만
고치면 갈립니다:

| | |
|---|---|
| `before` | 임팩트 **0.3초 전**. 그 프레임에 **차는 다리 무릎각이 없으면** 가장 가까운 잡힌 프레임(동률이면 **이른 쪽**). 🔴 **`[첫 유효, impact-1]` 안에서만** 고릅니다 — 안 가두면 임팩트 **뒤**가 「직전」으로 나옵니다 |
| `impact` | `segment_phases` 의 `extension_peak` |
| `after` | 임팩트 **+1초**. 단 **마지막 유효 프레임**을 넘지 않습니다 — 물러섰으면 `after_clipped: true`. 🔴 기준이 `frames` 가 아니라 **마지막으로 사람을 잡은 프레임**입니다. `frames` 로 재면 뒤가 미검출로 끝나는 클립에서 **빈 스켈레톤**이 카드로 나갑니다 |
| `direction` | `impact - 1` 과 임팩트의 **차는 다리 발목 x**. 🔴 **`before` 와 재지 않습니다** — 그쪽은 되접는 도중일 수 있어 부호가 뒤집힙니다 |

🔴 **지켜 주셔야 할 것**

- **못 잡은 프레임은 `null` 로 자리를 지킵니다.** 빼고 압축하지 마세요 —
  배열 인덱스가 곧 프레임 번호이고, 어긋나면 세 순간이 **엉뚱한 자세**를
  가리킵니다. 스켈레톤은 어느 쪽이든 그럴듯해 보여 눈으로도 안 잡힙니다
- **0~1로 자르지 마세요.** 화면 밖으로 나간 관절은 실제로 프레임 바깥
  좌표입니다. 자르면 발이 가장자리에 **붙어 있는 것처럼** 그려집니다
- **`features` 는 한 키도 안 늘었습니다** — 형제 블록이라 판정 입력이
  그대로이고, 점수·등급은 이 변경으로 한 자리도 안 바뀝니다

🔴 **크기 — 봉투가 13배가 됩니다** (2026.09.15 실측, 선수 영상 2편)

| | |
|---|---|
| 기본 격자 | **30fps · 300프레임 = 10초** (`DEFAULT_TARGET_FPS` 30 · `DEFAULT_MAX_FRAMES` 300) |
| `skeleton` 넣기 전 | **31 KB** |
| 넣은 뒤 | **398 KB** — 그중 `skeleton` 이 **316 KB (79%)** |

🔴 **앞서 「약 50KB」라고 적었던 것을 정정합니다** — 그 값은 15fps·150프레임을
가정했는데 실제 기본 격자가 **두 배**입니다. `storage.upload_json` 이 `indent=2`

## `card` — 추천 판의 설명 칸 (2026.09.16 추가, `paik` 27번)

지금 화면(`SquadSuggest.tsx`)은 후보마다 이름 아래 **한 줄 + 불릿 둘**을
붙박이 문자열로 그립니다. 그 자리를 분석으로 채웁니다.

```json
"card": {
  "title": "채찍이 된 다리",
  "notes": ["차는 다리 뻗기가 이번 동작의 강점입니다", "골반 돌리기는 아직 아쉽습니다"]
}
```

| | |
|---|---|
| `title` | 🔴 **받은 칭호일 때만** 채웁니다. 못 받았으면 **`null`** — 화면은 그때 이름 아래를 **비우면 됩니다**. 0등급의 「무너지는 축」을 수식어로 달지 않으려는 자리입니다 |
| `notes` | **한 줄 또는 두 줄.** 🔴 **두 줄을 채우려고 지어내지 않습니다** — 전부 잘했으면 아쉬운 줄이 없고, 전부 못했으면 강점 줄이 없습니다 |
| 수식어와 불릿 | **겹치지 않습니다** — 수식어는 **칭호**, 불릿은 **항목 이름**으로 씁니다 |

🔴 **경기 기록은 여기 없습니다.** 지금 붙박이에 섞여 있는 「활동량이 많고
꾸준합니다」·「10경기 연속」·「수비 가담이 성실합니다」는 **경기·출전 기록**이지
이 분석이 잰 것이 아닙니다. 그런 줄을 함께 쓰시려면 **출처가 다른 줄**로 받아야
하고, 🔴 **에이전트가 만든 줄과 섞어 한 목록에 두면 어디까지가 측정인지
사라집니다** — 화면에서 구분해 주세요.

**모델이 쓰지 않습니다** — 아래 `summary` 와 같은 이유입니다(코드가 짓고, 같은
판정이 같은 문장을 냅니다).

## `summary` 는 **모델이 쓰지 않습니다**

`evidence`(항목별 근거 문장)는 EXAONE 이 쓰지만 **요약은 코드가 짓습니다**
(`scoring.summarize`). 등급이 가장 높은 항목과 가장 낮은 항목의 칭호를 엮습니다.

- **숫자를 쓸 자리를 안 만듭니다.** 근거 문장 쪽에서는 이것을 지키는 데 2회차가
  걸렸고 아직 1건이 남아 있습니다(미결 23번)
- **같은 판정이 같은 문장을 냅니다** — 재현됩니다
- 🔴 **없는 것을 지어내지 않습니다**: 전부 잘했으면 아쉬운 점을 만들지 않고,
  전부 못했으면 강점을 만들지 않으며, **1등급을 「강점」이라 부르지 않습니다**
- 검사는 `tests/test_summary.py` (`rubrics/` 의 전 루브릭 × 등급 전 조합)

모델이 쓰는 코칭 문장으로 바꾸는 것은 **별도 회차 + 사전 등록**입니다.
「더 나은 요약」은 정답이 없어 좋아졌는지 판정할 방법이 없습니다.
