# 미결 6번 — 스윙 측 자동 판별의 한계, 현재 동작점에서 재계산

[미결 6번](../../../jekyll/pages/pending.markdown)에 적힌 travel 수치
(야구 18.2 대 27.6, 농구 16.30 대 16.09)는 **실효 12.5fps / 11.99fps에서 나온
값**이다. `DEFAULT_TARGET_FPS`가 15에서 30으로 올라가면서 동작점이 25fps /
23.98fps로 바뀌었는데, 두 클립의 포즈가 어디에도 남아 있지 않아 **확인하려면
매번 GPU가 필요했다.** 그 검증 불가를 없앤 것이 이 폴더다.

production code는 **import만** 한다. `agent/src/`·`agent/rubrics/`를 수정하지 않는다.

## 실행

```bash
cd agent
.venv/bin/python eval/pending6_side/extract.py     # GPU 필요, 약 50초, 1회만
.venv/bin/python eval/pending6_side/recompute.py   # GPU 불필요, 1초
```

`cache/*.npz`가 이미 있으면 `extract.py`는 건너뛴다. **덤프가 저장소에 들어
있으므로 보통은 `recompute.py`만 돌리면 된다.**

## 입력과 산출

| | 경로 | 크기 | 비고 |
|---|---|---|---|
| 입력 | `agent/data/{baseball_pitch_trim,bball_layup_trim}.mp4` | 11MB | `.gitignore` 대상 |
| 덤프 | `eval/pending6_side/cache/*.npz` | **32KB** | 저장소에 커밋 |

```
<clip>.npz
  keypoints    (T, 17, 3) float64   — COCO-17, x·y·신뢰도
  source_fps   ()         float64
  sampled_fps  ()         float64   — read_frames의 실효 fps
  target_fps   ()         int64     — 뽑을 때의 DEFAULT_TARGET_FPS (=30)
  obj_<이름>   (T, 3)     float64   — 도구 궤적 (sports_ball)
```

`candidates/`·`cache/` 보존과 같은 판단이다([PRESERVED_ASSETS](../phaseA/PRESERVED_ASSETS.md))
— 32KB에 GPU 없는 재해석이 붙는다.

## 옛 동작점을 같은 덤프에서 낸다

`read_frames`는 **정수 간격**으로 솎으므로 두 클립 모두 target 15에서 step=2였다
(25/15 → round 2, 23.98/15 → round 2). 즉 target 15의 프레임 집합은 target 30
집합의 정확한 `[::2]` 부분집합이고, ViTPose는 프레임마다 독립으로 도므로
**솎아 낸 결과는 그 fps로 다시 돌린 것과 같다.** `recompute.py`가 이 성질로
옛 수치와 새 수치를 한 덤프에서 나란히 낸다.

검증: 재계산한 옛 수치가 기록과 소수점까지 일치한다 — 야구 18.20 대 27.58
(기록 18.2 대 27.6), 농구 16.30 대 16.09 (기록과 동일).

## 결과 (2026-09-02)

| 클립 | 사지 | 옛 12.5/12.0fps | 현재 25/23.98fps | 판별 |
|---|---|---|---|---|
| 야구 투구 | arm | 던지는 왼팔 **18.20** 대 글러브 오른팔 **27.58** (마진 34.0%) | 23.53 대 33.13 (마진 29.0%) | **뒤집힌 채 그대로** |
| 야구 투구 | leg | 18.11 대 7.07 (마진 60.9%) | 18.87 대 8.95 (마진 52.5%) | 그대로 (left) |
| 농구 레이업 | arm | 16.09 대 **16.30** (마진 1.3%) | 17.05 대 **18.67** (마진 8.7%) | 그대로 (right, 맞는 쪽) |
| 농구 레이업 | leg | 6.07 대 9.79 (마진 38.0%) | 6.47 대 10.25 (마진 36.8%) | 그대로 (right) |

**샘플링을 두 배로 올려도 야구의 뒤집힘은 남는다.** 마진이 34% → 29%로 줄었을
뿐이다. 레이업은 1.3% → 8.7%로 벌어졌지만 여전히 얇다.

어느 쪽이 옳은지는 **라벨이 있어야 말할 수 있다.** 여기서 "뒤집혔다"고 쓴 것은
`identify_limb` 주석이 기록한 라벨(던지는 팔 = 왼쪽)을 그대로 쓴 것이다.

## docstring의 인과는 실측과 반대다

`identify_limb` 주석은 뒤집힘의 원인을 이렇게 적었다:

> 12.5fps에서 릴리스는 두 프레임 안에 끝나 경로가 짧은 반면, 글러브 팔은 내내
> 크게 돌기 때문이다. 잘못 잡힌 관절이 프레임마다 튀며 경로를 쌓는 것도
> 더해진다(글러브 팔 신뢰도 0.3~0.6).

세 주장 모두 이 덤프와 맞지 않는다.

| 주장 | 실측 |
|---|---|
| 던지는 팔의 경로가 두 프레임에 몰린다 | 12.5fps에서 경로가 가장 긴 두 프레임의 비중이 던지는 팔 **21%**, 글러브 팔 **32%** — 몰려 있는 쪽은 글러브 팔이다 |
| 글러브 팔은 내내 크게 돈다 | 위와 같다 — 글러브 팔이 더 국소적이다 |
| 글러브 팔 신뢰도 0.3~0.6 | 체인 중앙값 **0.77** (세 관절이 모두 0.6 이상인 프레임 49%). 절반이 게이트 아래로 내려가는 것은 맞지만 값의 범위는 다르다 |

fps를 두 배로 올렸을 때 travel은 던지는 팔에서 조금 더 늘어난다(×1.29 대
×1.20) — 빠른 구간이 덜 솎였다는 뜻이라 인과의 **방향**은 맞다. 그러나 29%
격차를 메울 크기가 아니다. **뒤집힘의 원인은 아직 밝혀지지 않았다.**

## 하지 않은 것

- **판별 로직 변경.** `identify_limb`·`identify_legs`·travel 식을 손대지 않았다.
- **프레임 수 정규화.** 처방이 아니다. 다만 여기 적었던 근거("평가셋 39클립에서
  갈림이 오히려 늘었다 — arm 1→2, leg 6→7")를 **철회한다** (2026.09.03).
  travel을 **양쪽 같은 프레임 수로** 나누면 `L/d >= R/d`는 `L >= R`와 같은
  부등식이라 **어떤 클립에서도 고르는 쪽이 바뀔 수 없다.** 산술적으로 불가능한
  주장이었고, 재현해도 39클립 전부 그대로다(arm 1/38, leg 6/38로 불변).
  좌우 각각의 **관측 비율로 할인**하는 변형은 실제로 값이 바뀌지만
  (arm 3/38·6/38, 나누기 판이면 6/38·6/38) 기록된 (2, 7)과는 맞지 않는다.
  처방이 아니라는 결론은 유지하되 **근거는 미결 7번 본문으로 돌린다.**
- **라벨링.** 어느 쪽이 옳은지 가르려면 사람 라벨이 필요하고, 그것은 다음 단계다.
- 세 번째 클립(`bball_shot.mp4`, 농구 점프슛)은 미결 6번의 travel 수치에
  등장하지 않아 덤프하지 않았다.
