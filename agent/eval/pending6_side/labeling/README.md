## 🔴 이 평가셋은 전부 야구 **타격**이다 — 두 손 스윙

작업 중에 확인했고, 과제의 전제를 흔든다. `identify_limb(limb="arm")`은
"말단이 더 많이 움직인 쪽"을 고르는데, **배트를 두 손으로 잡으면 양 손목이
같은 궤적을 그린다.** 판독 이미지에서 두 손목의 `L`·`R` 글자가 겹쳐 뭉쳐
보일 정도였다(그래서 표기 위치를 갈라 놓았다).

🔴 **처음엔 얇은 마진과 fps 갈림을 그 증거로 적었는데, 재계산해 보니 아니다**
(2026.09.03 정정). production과 같은 정규화 좌표로 다시 재면 arm 마진 중앙값
0.147로 leg(0.090)보다 **두껍고**, 15↔30 갈림도 arm 1/38 대 leg 6/38로
**적다.** 두 손 스윙이라고 마진이 0으로 뭉개지지는 않는다 — 두 손목이 붙어
있어도 배트 위쪽 손이 더 먼 호를 그리기 때문으로 보인다.

**그래서 "두 손 스윙인가"는 마진으로 못 답한다. 라벨이 답한다.**
남은 사실은 그대로다 — 두 손이 배트를 함께 잡으면 "스윙 팔 대 지지 팔"이라는
구분 자체가 없고, 그때 마진이 가리키는 것은 `top_hand`이지 스윙 팔이 아니다.

**"전부"의 한계도 적어 둔다.** 39클립은 Kinetics `hitting baseball` val
전수(`ann/hb_val.csv`)라 **라벨이 전부 타격**인 것은 맞다. 그러나
`phaseA_metadata.csv`는 이렇게 적고 있다.

| | |
|---|---|
| 사람이 실제로 본 것 | 20/39. 나머지 19는 `camera_angle`부터 `미검증`이다 |
| 라벨이 의심되는 것 | `IYFifBJ9lH8` — "실내 트랙. 라벨 의심(투구로 보임)" |
| 스켈레톤이 타자가 아닌 것 | `O2GSaYqH8JY`(공 줍는 코치) · `3R1kvNrGJK0`(심판/포수) · `w-AQcjcoDyA`(신발 클로즈업) |
| `usable_for_phase_B` | yes 7 · maybe 6 · **no 26** |

그래서 `subject_ok` 칸이 장식이 아니다 — **분모를 정하는 칸**이다.

**그래서 서식에 두 칸을 더 두었다.**

- `swing_arm`에 **`both`** 를 허용한다. 억지로 한쪽을 고르게 하면 그 라벨은
  잡음을 정답으로 승격시킨다
- **`top_hand`** (배트 위쪽을 잡은 손)를 함께 받는다. 두 손 스윙에서도 항상
  정의되고 타격 자세와 1:1이라, `both`가 많이 나와도 쓸 수 있는 기준이 남는다

`both`가 다수로 나오면 그 자체가 이 항목의 답이 된다 — 자세한 것은
`AFTER_LABELS.md` 5절.

## 판독 자료 형식과 근거

**클립당 한 장**, 자세 시퀀스 6칸 + 전체 화면 1칸.

| 정한 것 | 근거 |
|---|---|
| **시점을 좌우 대칭 활동량으로 고른다** | 10초 클립에서 스윙은 1초 남짓이라 균등 간격은 동작을 놓친다. 그렇다고 한쪽 손목 이동량으로 고르면 **판정 대상인 그 신호로 화면을 고르는 것**이라 앵커링이다. 양쪽 손목·발목 이동량의 **합**은 좌우 대칭이라 *언제*만 고른다 |
| **정지 프레임 6장** (영상 아님) | 영상은 재생·되감기에 시간이 든다. 6장이면 준비→임팩트→팔로스루가 한눈에 들어온다 |
| **스켈레톤을 그린다** | 헐렁한 옷·역광·원거리에서 팔다리 구분이 느리다. 양쪽을 **같은 색·같은 굵기**로 그려 어느 쪽도 강조하지 않는다 (B-4 검수 패킷이 후보 상자를 전부 같은 색으로 그린 것과 같은 이유) |
| **L/R을 관절에 직접 쓴다** | 화면 좌우와 인체 좌우가 다르고 정면 구도에서 뒤집힌다. 머릿속 변환을 시키면 느려지고 틀린다. 모델이 붙인 해부학적 좌우를 쓰므로 알고리즘의 답과 **같은 좌표계**다 |
| **L은 왼쪽 위, R은 오른쪽 아래** | 두 손 그립에서 손목이 겹쳐 `LR`로 뭉쳐 읽히지 않았다. 클립 내용과 무관한 고정 규칙이라 어느 쪽도 유도하지 않는다 |
| **글자·선은 축소한 뒤에 그린다** | 원본에 그리고 줄이면 4K 클립에서 L/R이 안 보인다 — 첫 판에서 실제로 그랬다 |
| **전체 화면 칸을 함께 둔다** | 잘라낸 그림만 보면 **대상 선수를 잘못 골랐을 때 알 수 없다.** 실제로 `O2GSaYqH8JY`는 공 줍는 사람에게 스켈레톤이 붙어 있고, 이 칸 덕분에 사람이 잡아낸다 (`subject_ok` 칸) |

### 앵커링 — 대조 정보는 분리했다

자동 판별 결과·마진·15fps 갈림 여부를 **판독 화면에 넣지 않았다.**
`reference_AFTER_LABELING.csv`에 따로 두고 라벨 확보 후에만 본다.

근거는 셋이다.

1. **정확도를 재려는 대상을 먼저 보여주면 그 정확도는 측정이 아니다.**
   특히 마진이 얇은 클립(arm 8/39·leg 13/39가 5% 미만)일수록 사람도 애매한데,
   바로 그 구간에서 앵커링이 가장 세게 작동한다
2. B-4 선례가 같은 이유로 후보 상자를 전부 같은 색으로 그렸다
3. 순서도 앵커링이다 — 서식은 마진순이 아니라 **clip_id 알파벳순**이다

## 입력 형식

`labels.json`(프레임 단위, `box_index`)과 성격이 달라 **별도 CSV**로 했다.
근거: 대상이 39행뿐이고 클립당 1행이라 JSON 구조가 이득이 없다. CSV는
스프레드시트로 바로 열려 도구 설치가 필요 없다.

**`label_cli.py` 같은 입력 도구는 만들지 않았다.** 그쪽은 117개 프레임을
하나씩 물어야 해서 필요했지만, 여기서는 이미지를 보며 표를 채우는 편이 빠르고
터미널은 이미지를 못 띄운다.

값은 `L` · `R` · `both`(팔만) · `unclear` · `na`, 그리고 `subject_ok`는
`y`/`n`. **"판정 불가"를 두 값으로 나눈 것이 의도다** — `unclear`는 가려져서
안 보이는 것이고 `na`는 애초에 동작이 없는 것이라, 나중에 분모에서 빼는
방식이 다르다.
