# 사전 등록 — LoRA 파인튜닝 1회차 (미결 23번 ④)

**작성 2026-09-18 09:48 · 결과를 보기 전에 고정한다.** 아래 수치는 결과를 보고
고치지 않는다. 고쳐야 할 이유가 생기면 **다음 회차의 사전 등록**에 쓴다.

## 0. 왜 지금 — 그리고 무엇이 아닌가

프롬프트로 아홉 회차(가-2 ~ J)를 돌린 뒤 방향 오독이 **4/30 언저리에서 안
움직인다.** E·H·I 는 「한쪽을 조이면 다른 쪽이 무너진다」로 전부 되돌렸다.

🔴 **이것은 제품 적용 회차가 아니다.** 어댑터를 vLLM 에 붙이는 것(`--enable-lora`)·
배포·`sync_model.sh` 는 **이 회차 밖**이다. 여기서 정하는 것은 **「파인튜닝이
프롬프트가 못 넘은 벽을 넘는가」 하나**다.

🔴 **`features` 를 건드리지 않는다.** 판정 입력이 그대로이므로 B-6 재실행을
부르지 않는다. `src/` 도 고치지 않는다 — 이 폴더의 스크립트가 production 을
**import 만** 한다.

## 1. 라벨을 어디서 — 「사람이 검증한 선별」이지 「AI 단독 판독」이 아니다

🔴 **로드맵 2절**: AI 단독 판독은 부정적 결론의 근거로는 쓰고 **정답으로
승격하지 않는다.** 2026-09-17 회차에서 담당자(모델) 진단이 **다섯 번** 틀렸다.
그래서 선별을 셋으로 가른다.

| 누가 | 무엇을 가르나 | 성격 |
|---|---|---|
| **코드** | R1(「등급」 낱말) · R2(구간 표기) · R3(지어낸 수치) · ~~`metric_ref` 유효~~ · **앵커 문장 통째 베끼기** | 결정론 |
| **모델(담당자)** | 후보가 **`criterion.plain_for(grade, value)` 가 말하는 방향과 같은 방향인가** | 🔴 대조 — 제 취향이 아니라 **코드가 낸 기준 문장**과 맞춰 본다 |
| **사람(정상호)** | 위 선별에서 **무작위 30개**를 보고 동의/부동의 | 검증 |

🔴 **`metric_ref` 조항을 걷었다 (09:53, 후보 문장을 읽기 전 · 자리별 자동통과
**수치만** 보고).** production 의 `Judge._validate` 가 무효한 `metric_ref` 를
조용히 `band_metric` 으로 떨어뜨리므로, 그것으로 후보를 버리면 **제품이 버리지
않는 것을 버리는** 거르개다. 실제로 첫 실행에서 **42자리 전부 자동통과 0** 이
나왔다. 문장은 그대로 두고 **거르개만 다시 계산한다**(재생성 없음).

🔴 **50개 → 30개로 줄였다 (09:50, 선별을 돌리기 전).** 사용자 요청(오늘 안에
최소 시간)이고, **비율(84%)은 그대로**라 판정 성격이 안 바뀐다. 표본이 작아져
**신뢰구간이 넓어지는 것**이 대가다 — 30개 중 25개면 실제 정확도가 70% 대일
가능성이 남는다. 🔴 **이 사실을 결과에 적는다.**

🔴 **합격선: 30개 중 25개(84%) 이상 동의.** 미달이면 **그 자리에서 멈춘다** —
학습을 돌리지 않고, 오늘은 ① 템플릿 갈래로 돌린다. 근거: 선별 정확도가 84%
미만이면 라벨의 오염이 프롬프트로 남은 오독률(≈13%, 4/30)과 같은 규모가 되어
**무엇을 고쳤는지 가를 수 없다.**

🔴 **학습 목표가 사실상 「템플릿 방향」이 된다.** 정답 출처가 `grades_plain`
하나뿐이라 그렇다. 그러므로 이 회차가 합격해도 **「모델이 자기 판단으로
방향을 알게 됐다」로 읽지 않는다** — 「템플릿의 방향을 문장 다양성과 함께
가져왔다」가 말할 수 있는 전부다.

## 2. 무엇을 학습하고 무엇으로 평가하나 — 자리를 나눈다

| | 루브릭 | 자리 |
|---|---|---|
| **학습** | `football/instep_shot` | **42** (2등급 12 · 1등급 16 · 0등급 14) |
| **평가** | `football/inside_pass` | **38** (2등급 10 · 1등급 14 · 0등급 14) |

같은 종목 다른 항목이라 **일반화를 본다.** 🔴 **평가 자리는 학습에 한 개도
쓰지 않는다.**

후보는 자리당 **12개**(temp 0.9 · top_p 0.95 · seed 고정). 12 인 이유: 실측에서
자동 거르기 통과율이 불확실하고, 8 개면 전부 탈락하는 자리가 생길 수 있다.

## 3. 기준선 — **오늘 다시 잰다**

지금까지의 80문장 대조(C0~J)는 **두 루브릭 합본**이고 감점 30 · 잘함 22 자리
기준이다. 오늘 평가는 `inside_pass` **38자리**(감점 28 · 잘함 10)뿐이라
**그 숫자와 직접 비교하지 않는다.**

🔴 **파인튜닝 전 모델로 같은 38자리를 오늘 먼저 돌려 `BASE` 로 삼는다**
(그리디, 지금 제품 경로 그대로). 학습 결과를 보기 전에 잰다.

## 4. 합격·불합격 — 결과를 보고 바꾸지 않는다

| | 기준 | 합격선 |
|---|---|---|
| **P-1** | 방향 오독 (감점 28자리, 절 단위 계기) | 🔴 **`BASE` 보다 2건 이상 적고, 절대 3건 이하** |
| **P-2** | 잘함 문장 오독 (10자리) | 🔴 **`BASE` 이하이고 절대 1건 이하** |
| **P-3** | R1 · R2 | **각 0건** |
| **P-4** | R3 (지어낸 수치) | **`BASE` 이하** |
| **P-5** | 🔴 **고유 문장 가짓수** | **`BASE` 의 0.8배 이상** |

**P-1·P-2 를 동시에** 넘어야 합격이다 — 한쪽만 좋아지고 다른 쪽이 무너진 것이
E·H·I 세 회차다. **P-5 를 넣은 이유**: 학습 목표가 템플릿 방향이라 모델이
**자리마다 같은 한 문장으로 수렴**할 수 있다. 그러면 방향은 맞지만 산출물은
느린 템플릿이다 — J 회차가 잰 「템플릿 37~39가지 vs 모델 76가지」가 그 축이다.

**불합격이면 어댑터를 버린다.** 제품 코드·루브릭은 이 회차에서 한 줄도 안
바뀌므로 되돌릴 것이 없다.

## 5. 판독 방법 — 있는 계기를 그대로 쓴다

- 방향 오독: `split_clauses.py`(절 단위) + `check_evidence.py`(R1·R2·R3).
  🔴 **규칙을 넓히지 않는다.** D 회차가 드러낸 구멍(반대 조각 주장·제3의
  주장·「문제없다」)은 **그대로 두고 관례대로 센다** — 넓히면 앞 회차와
  비교가 끊긴다
- 🔴 **판독은 담당자(모델)가 한다.** 그래서 이 회차의 결론은 **부정적 방향
  (「안 넘었다」)에 강하고 긍정적 방향에 약하다.** 합격이 나오면 그것은
  **「사람이 볼 값이 있다」**는 뜻이지 「검증됐다」가 아니다

## 6. 학습 설정 — 실측에 근거한 값 (2026-09-18, RTX 3050 8GB)

| | 값 | 근거 |
|---|---|---|
| 방식 | **LoRA SFT** (전체 파인튜닝 안 함) | 어댑터는 껐다 켤 수 있어 대조가 된다 |
| 자리 | `q_proj`·`v_proj`, r=16 | 실측 1,400 tok/s · VRAM 5.4GiB (bs 4×512) |
| epoch | 3 | 500쌍 × ~700토큰 → **4분/epoch** |
| 구현 | 🔴 **순수 torch** (`peft`·`trl` 안 씀) | 60줄이라 별도 venv 를 안 만들어도 되고, 에이전트 venv 에 학습 의존성을 안 들인다 (README 5-2 의 torch 깨짐). **대가: 어댑터가 peft 형식이 아니라 vLLM 에 그대로 못 붙는다** — 채택되면 그때 다시 굽는다 |
| 가중치 | `Judge.load()` 가 적재한 것 그대로 | 커밋 해시 고정(미결 11번)이 거기 있다 — 다시 부르면 고정이 갈라진다 |
