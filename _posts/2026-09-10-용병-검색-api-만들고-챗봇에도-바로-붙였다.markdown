이전 세션에서 시작한 용병 매칭 작업을 이어받았다. `user` 테이블에 매칭용
필드(`preferred_positions`·`available_slots`·`location`·`skill_summary`·
`is_searchable`·`skill_embedding`)를 얹는 마이그레이션과 ORM 매핑까지는 이미
끝나 있었다(미결 `min` 16번). 그 위에 실제로 쓰는 애플리케이션(라우터·
유스케이스·pgvector 저장소·Gemini 임베딩 어댑터)을 `user` 컨텍스트 안에
전부 만들고 `docs/api-contract.md` 3-11절로 규격을 냈다(미결 `min` 17번).

**SFR-006(적합도)·SFR-007(추천)과는 다른 기능이라는 것을 표로 명확히 갈랐다** —
이쪽은 지원 전에 팀이 능동적으로 하는 검색이고, 그 둘은 지원 후 채점·추천이다.
포지션 인코딩은 `"<sport_code>:<code>"` 문자열로 — 포지션 약칭이 종목 간
겹쳐서(`position` 테이블과 같은 이유) — DB 테스트로 야구·농구 `C`가 안 섞이는
것까지 확인했다.

#### 정정 — "다음 단계 결정"이라고 적었던 것을 바로 뒤집었다

`docs/client-contract-changes.md` 30번을 처음 낼 때는 "`www/` 연동은 지금
반영할 항목이 아니다"라고 적었다. 그런데 검색 API를 다 만들고 나니 챗봇
(`MatchBot.tsx`, 미결 `min` 7번의 흐름 B)에 흐름 D로 붙이는 일 자체는 작지
않은 일이지만 지금 붙이지 않을 이유가 없어서 **바로 이어서 구현했다.**
`www/src/app/api/chat/route.ts`가 검색 API를 부르고 결과를 다시 Gemini에
넣어 소개 문장으로 엮는다 — RAG의 검색+생성 구조다. 앞서 "당장 할 일은
아니다"라고 냈던 문서 세 곳(`api-contract.md`·`client-contract-changes.md`·
`pending.markdown` 17번)을 전부 이 결정대로 고쳐 뒀다 — 조용히 값만 바꾸면
읽는 사람이 자기가 잘못 읽은 줄 안다.

**같은 날 안에 그 나머지(정어진 몫)까지 마저 했다.** 사용자가 "여기서 지금
하겠다"고 해서, 공유 파일 규칙(`fastapi/CLAUDE.md`)의 예외로 `app/main.py`에
`mercenary_router`를 직접 등록했다 — 등록 목록을 검사하는
`tests/user/adapter/test_auth_router.py`의 openapi 경로 집합도 새 경로 둘을
반영해 함께 맞췄다.

**`GEMINI_API_KEY` 배포에서 실제 버그를 하나 잡았다.** 사용자가 fastapi
전용으로 새로 발급한 키를 받아(`www/`가 쓰는 키와 분리하는 편이 낫다고
권했고 그렇게 했다) 로컬에서 먼저 `GeminiEmbeddingAdapter`를 직접 호출해
봤는데, 처음 코드에 적어 둔 모델 `text-embedding-004`가 **이미 은퇴돼
`embedContent`에서 404(NOT_FOUND)** 였다. `client.models.list()`로
`embedContent`를 지원하는 모델을 뽑아 보니 `gemini-embedding-001`이 있었고,
그걸로 바꾸니 768차원 벡터가 정상적으로 돌아왔다 — `gemini_embedding_adapter.py`
코드 자체를 정정했다. 가짜 키로 끝냈다면 배포 뒤 첫 검색 요청에서야 이
오류를 만났을 것이다. 이후 키를 배포 서버 `~/supersub/app/fastapi/.env`에
넣고(0600 유지) `supersub-api` 재시작·`/health` 200을 확인했다. 검색 권한
범위(팀 주장 한정 여부)는 사용자가 "지금은 현행 유지"로 정했다 — 코드
변경 없음.

앞서 이 글과 세 문서(`api-contract.md`·`client-contract-changes.md`·
`pending.markdown` 17번)에 "아직 안 됐다"고 적어 둔 것도 전부 이 상태로
다시 고쳐 뒀다.

확인: 배선 뒤 `pytest` 507 passed(비-DB)/12 failed·28 errors — 전부 이
세션에 로컬 Postgres가 안 떠 있던 탓(기존 DB 테스트도 같은 모양으로 실패)이고
새 코드로 인한 회귀는 없었다. `alembic heads` 단일. `www` 쪽은 vitest
422 passed / 3 failed(`rubricFocus.test.ts`, 이 작업과 무관한 기존 실패 —
이미 미결 `ho` 29번에 백성검 담당으로 잡혀 있는 라벨 불일치라 새로 올리지
않는다) / 1 skipped.
