# k3s로만 빌드·구동한다 — docker-compose 금지

> **상태:** 정책 확정 + 설정 가이드 · 2026-09-09 · **작성:** 박민호
> **적용 범위:** 로컬 개발 환경과 EC2 운영 환경 둘 다. 지금 저장소엔
> `docker-compose*` 파일이 없고, **앞으로도 만들지 않는다.**

## 0. 정책

🔴 **애플리케이션의 빌드와 구동은 k3s로만 한다. docker-compose는 쓰지 않는다.**

- 이미지는 `docker build`로 만들지만, 그걸로 컨테이너를 직접 띄우거나
  `docker-compose up`으로 여러 컨테이너를 묶지 않는다 — **k3s(Deployment)로만
  띄운다.**
- 로컬 dev와 EC2 운영이 같은 방식(k3s 매니페스트)을 쓰게 해서, "로컬에선
  되는데 배포에서 안 된다"는 차이를 줄이는 것이 목적이다.
- DB처럼 상태를 갖는 서비스는 **지금은 예외**다 — 아래 3절 참고. k3s
  Deployment/StatefulSet으로 옮기는 건 각 서비스 소유자가 정할 일이다.

이 문서는 그 정책을 실제로 지킨 첫 사례(2026-09-09, `supersub-api`를 AWS
`supersub`와 로컬 WSL 양쪽 k3s에 올린 것)를 절차로 남긴 것이다. **다음에 EC2에
새 k3s를 놓을 때(우분투 포함) 이 절차를 그대로 따라간다.**

## 1. k3s 설치

```bash
curl -sfL https://get.k3s.io | sudo sh -
```

- OS 상관없이(Ubuntu·Debian·Amazon Linux 전부) 동일한 명령이다. 공식
  설치 스크립트가 배포판을 감지해서 systemd 서비스(`k3s.service`)로 등록한다.
- 확인:
  ```bash
  sudo systemctl is-active k3s          # active
  sudo k3s kubectl get nodes            # Ready
  ```
- k3s는 자체 containerd를 쓴다 — Docker 데몬이 없어도 k3s 자체는 돈다.
  Docker는 **이미지를 빌드할 때만** 필요하다(2절).

## 2. 이미지 빌드용 docker 설치

k3s의 containerd만으로는 이미지를 못 만든다. 빌드는 여전히 `docker build`로
하고, 만든 이미지를 k3s의 containerd로 옮겨 넣는 식이다.

| OS | 설치 |
|---|---|
| Amazon Linux 2023 | `sudo dnf install -y docker && sudo systemctl enable --now docker` |
| Ubuntu | `sudo apt-get update && sudo apt-get install -y docker.io && sudo systemctl enable --now docker` |
| WSL(로컬) | 이미 Docker Engine이 깔려 있으면 이 단계 생략 — `docker version`으로 먼저 확인 |

## 3. 애플리케이션 이미지 빌드 → k3s로 반입

Dockerfile 예시(파이썬 백엔드 기준 — 실제로 쓴 것):

```dockerfile
FROM python:3.14-slim
WORKDIR /app
COPY requirements.lock.txt .
RUN pip install --no-cache-dir -r requirements.lock.txt
COPY . .
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
```

🔴🔴 **`.dockerignore` 없이 `COPY . .`를 쓰지 않는다 — 실제로 `.env`가
이미지에 통째로 들어가 Docker Hub까지 올라간 적이 있다**(2026-09-09,
`jekyll/pages/pending.markdown` min 11번). `.env`엔 DB 비밀번호·`JWT_SECRET`
같은 진짜 비밀값이 있다. **Dockerfile을 새로 만드는 자리마다 반드시 같이
만든다**:

```
# .dockerignore
.env
.env.*
!.env.example
.venv
__pycache__
tests
.git
```

빌드 뒤엔 **이미지 안을 직접 열어서 확인한다** — `.dockerignore`를 믿지만
말고:

```bash
docker run --rm <이미지명>:latest ls -la /app | grep -E '\.env|\.venv'
# 아무것도 안 나와야 정상이다
```

```bash
docker build -f <Dockerfile 경로> -t <이미지명>:latest <빌드 컨텍스트 경로>
docker save <이미지명>:latest | sudo k3s ctr images import -
```

🔴 **`k3s ctr images import`는 root가 필요하다** — containerd 소켓
(`/run/k3s/containerd/containerd.sock`)이 `root:root 660`이라 일반 사용자
그룹(예: `docker` 그룹)으로는 못 건드린다. `sudo` 없이 우회할 방법은 없었다.

**Dockerfile·`.dockerignore`는 이제 저장소에 커밋돼 있다** —
`fastapi/Dockerfile`, `fastapi/.dockerignore`. 위 보안 사고 때문에 `.dockerignore`를
그 서비스 저장소에서 git으로 관리하는 걸 우선했다. 이미지 태그 전략(버전
태그 vs `latest` 하나만 쓰는 지금 방식)은 아직 안 정했다 — 여전히 그 서비스를
소유한 쪽(`fastapi/`라면 정어진)이 판단할 일이다. 자세한 내용은
`jekyll/pages/pending.markdown` **min 11번**.

### 3-1. (권장) 레지스트리로 push — 서버마다 다시 빌드하지 않는다

위 `k3s ctr images import`는 **그 서버에서 직접 빌드했을 때만** 쓸 수 있다.
여러 서버(로컬·EC2 여러 대)가 같은 이미지를 쓰게 하려면 Docker Hub 같은
레지스트리를 거치는 편이 낫다. 실제로 AWS `supersub`에서 이 방식으로 바꿨다.

```bash
docker login -u <계정>              # 데몬 소켓이 필요 없어서 sudo 없이도 된다
docker tag <이미지명>:latest <계정>/<레포>:latest
sudo docker push <계정>/<레포>:latest   # push는 데몬이 필요해서 sudo가 있어야 한다
```

🔴 `sudo docker push`를 쓰면 **root 계정의 docker config**를 본다 — `docker
login`을 일반 사용자로 했다면 root는 그 로그인 정보를 못 본다. 아래 둘 중
하나로 맞춘다.
- root로 다시 로그인: `sudo docker login -u <계정>`
- 또는 일반 사용자 config를 지정: `sudo docker --config /home/<사용자>/.docker/config.json push ...`

**private 레포를 쓰는 이유**: 이미지 안에 `COPY . .`로 앱 소스가 그대로
들어간다. public으로 하면 누구나 pull 받아서 소스를 통째로 꺼내 볼 수 있다.

k3s가 그 private 레포에서 pull하려면 **k8s Secret**이 하나 더 필요하다 —
로그인해둔 docker config를 그대로 재사용한다:

```bash
sudo k3s kubectl create secret generic dockerhub-cred \
  --from-file=.dockerconfigjson=/root/.docker/config.json \
  --type=kubernetes.io/dockerconfigjson
```

Deployment의 `image`를 `<계정>/<레포>:latest`로, `imagePullPolicy: Always`로
바꾸고 `imagePullSecrets: [{name: dockerhub-cred}]`를 추가한다(5절 예시에
반영돼 있다). 확인은 `kubectl describe pod`의 Events에 `Pulling image` →
`Successfully pulled`이 찍히는지로 한다 — 로컬에 같은 이름의 이미지가 이미
있어도 `Always`면 매번 레지스트리에서 새로 받아온다.

## 4. 설정 주입 — `.env` → k8s Secret

```bash
sudo k3s kubectl create secret generic <이름>-env --from-env-file=<.env 경로>
```

🔴 비밀번호·토큰이 든 파일이다. **이 명령의 출력이나 `.env` 내용을 화면에
`cat` 하거나 로그·문서에 붙여넣지 않는다.**

## 5. Deployment

실제로 쓴 매니페스트(포트·이미지명은 환경마다 다르게 채운다):

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: <서비스명>
  namespace: <네임스페이스>   # 6절 참고
spec:
  replicas: 1
  selector:
    matchLabels:
      app: <서비스명>
  template:
    metadata:
      labels:
        app: <서비스명>
    spec:
      hostNetwork: true                      # DB가 localhost만 듣는 구성일 때 필요
      dnsPolicy: ClusterFirstWithHostNet
      imagePullSecrets:                      # 레지스트리 pull 방식(3-1절)일 때만 필요
        - name: dockerhub-cred
      containers:
        - name: <서비스명>
          image: <계정>/<레포>:latest          # 로컬 import 방식이면 <이미지명>:latest
          imagePullPolicy: Always              # 로컬 import 방식이면 Never
          envFrom:
            - secretRef:
                name: <이름>-env
          ports:
            - containerPort: <포트>
          command: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "<포트>"]
```

- `hostNetwork: true`를 쓰는 이유: 지금까지 붙인 서버들은 DB가 `127.0.0.1`
  에서만 듣도록 되어 있다. 파드가 자체 네트워크 네임스페이스를 쓰면 그
  `127.0.0.1`이 DB가 아니라 파드 자신을 가리켜서 못 붙는다. 호스트
  네트워크를 그대로 쓰면 파드 안에서도 `127.0.0.1`이 호스트의 DB로 간다.
- 적용: `sudo k3s kubectl apply -f <매니페스트>`
- 확인:
  ```bash
  sudo k3s kubectl get pods -o wide
  curl -s localhost:<포트>/health
  ```

## 6. 네임스페이스 — 기존 워크로드와 섞이지 않게

같은 k3s 클러스터에 **이미 다른 프로젝트가 떠 있을 수 있다** — 로컬 WSL이
실제로 그랬다(`vps-detector`라는 이름의 무관한 다른 프로젝트가 먼저 있었다).

```bash
sudo k3s kubectl create namespace <이름>
sudo k3s kubectl -n <이름> apply -f <매니페스트>
```

새 서비스를 올리기 전에 **`kubectl get pods -A`로 이미 뭐가 떠 있는지부터
본다.** 남의 네임스페이스는 절대 건드리지 않는다.

## 7. CD — 새 이미지가 올라오면 자동으로 반영한다

🔴 **Docker Hub의 Webhook(레포 설정 → Webhooks)으로 EC2를 직접 부르지
않는다.** 두 가지 이유가 있다.

1. 지금 보안그룹은 22번만 열려 있다 — 웹훅을 받으려면 새 포트를 열어야
   하고, 그만큼 공격 표면이 늘어난다.
2. Docker Hub의 Webhook 요청엔 **서명이 없다.** URL을 아는 사람이면 누구나
   똑같은 요청을 보낼 수 있어서, 열어봐야 인증이 약하다.

대신 **EC2가 주기적으로 Docker Hub를 폴링**해서 새 digest가 있으면 스스로
재배포하게 한다 — 전부 나가는(outbound) 연결이라 포트를 하나도 새로 열
필요가 없다.

```bash
#!/bin/bash
set -euo pipefail

IMAGE="<계정>/<레포>:latest"
DEPLOYMENT="<서비스명>"
STATE_FILE="<홈>/k3s-trial/.last-digest"

sudo docker pull -q "$IMAGE" >/dev/null
CURRENT_DIGEST=$(sudo docker inspect --format='{{index .RepoDigests 0}}' "$IMAGE")
LAST_DIGEST=$(cat "$STATE_FILE" 2>/dev/null || echo "")

if [ "$CURRENT_DIGEST" != "$LAST_DIGEST" ]; then
    sudo k3s kubectl rollout restart deployment/"$DEPLOYMENT"
    sudo k3s kubectl rollout status deployment/"$DEPLOYMENT" --timeout=60s
    echo "$CURRENT_DIGEST" > "$STATE_FILE"
fi
```

systemd timer로 2분마다 돌린다(`OnBootSec=1min`, `OnUnitActiveSec=2min`,
`Unit=<서비스>.service`) — `User=ec2-user`로 두고 스크립트 안에서만 `sudo`를
쓰면, **AWS 기본 `ec2-user`가 이미 NOPASSWD sudo라 비밀번호 프롬프트 없이
백그라운드에서 잘 돈다.**

🔴 **`hostNetwork: true`인 Deployment는 `strategy: Recreate`로 둔다.**
기본값(RollingUpdate)이면 `rollout restart`가 새 파드를 먼저 띄우려다
기존 파드와 호스트 포트가 겹쳐서 `Pending`에 걸린다(8절 표 참고).
`Recreate`는 기존 파드를 먼저 끄고 나서 새 파드를 띄워서 이 문제가 안
생긴다.

**소스 코드가 바뀌면 이미지도 자동으로 다시 빌드되게** GitHub Actions를
붙인다(`.github/workflows/backend-docker-build.yml` 예시):

```yaml
name: 백엔드 이미지 빌드·Docker Hub push
on:
  push:
    branches: [main]
    paths:
      - "fastapi/**"
jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: fastapi
          file: fastapi/Dockerfile
          push: true
          tags: <계정>/<레포>:latest
```

GitHub 저장소 **Settings → Secrets and variables → Actions**에
`DOCKERHUB_USERNAME`·`DOCKERHUB_TOKEN`(Docker Hub Access Token, Read &
Write)을 미리 등록해둬야 한다 — 토큰 값은 문서·대화 어디에도 남기지 않는다.

전체 흐름: **`main`에 push → GitHub Actions가 빌드·push → EC2가 최대 2분
안에 감지해서 재배포.**

## 8. 함정 — 실제로 걸렸던 것들

| 증상 | 원인 | 조치 |
|---|---|---|
| 새 파드가 기존 서비스와 같은 포트를 쓰려다 충돌 | `hostNetwork: true`는 호스트 포트를 그대로 쓴다 — 이미 systemd 등으로 그 포트를 쓰는 서비스가 있으면 못 뜬다 | 트라이얼 단계에서는 **다른 포트**를 쓴다. 기존 서비스를 그대로 두고 새 포트로 검증한 뒤 전환은 별도 결정 |
| 로컬(WSL) 브라우저(Windows)에서 `127.0.0.1:<포트>`가 계속 로딩만 되고 안 뜬다 | **Windows 자체가 이미 그 포트를 쓰고 있으면** WSL2가 `127.0.0.1`을 WSL로 전달하지 못한다 | Windows 쪽에서 확인: `cmd.exe /c "netstat -ano \| findstr :<포트>"` (WSL 안에서 `cmd.exe`로 Windows 명령 호출 가능). 이미 쓰고 있으면 다른 포트로 바꾼다 |
| `CREATE EXTENSION vector` 실패 | 일반 `postgres` 이미지엔 pgvector가 없다 | `pgvector/pgvector:pg<메이저버전>` 이미지를 쓴다. 기존 데이터가 있는 볼륨이면 **같은 볼륨을 그대로 마운트**해서 이미지만 갈아타면 데이터가 보존된다 |
| `k3s ctr images import`가 계속 sudo를 요구 | containerd 소켓이 root 전용 | 우회 없음 — 그때그때 sudo로 실행한다. 자동화(CI 등)에 넣을 거면 이 단계를 root 권한이 있는 러너에서 돌려야 한다 |
| `denied: requested access to the resource is denied` (push 시) | `sudo docker push`가 **root의 docker config**를 봐서, 일반 사용자로 해둔 `docker login`이 안 보인다 | `sudo docker login`을 root로 다시 하거나, `sudo docker --config /home/<사용자>/.docker/config.json push ...`로 위치를 지정한다 |
| 레지스트리 방식으로 바꾸며 `kubectl apply`했더니 새 파드가 `Pending`, `didn't have free ports` | 단일 노드에서 `hostNetwork: true`인 Deployment는 롤링 업데이트 때 **새 파드와 기존 파드가 같은 호스트 포트를 동시에** 쓰려고 한다 | 기존 파드를 수동으로 지운다(`kubectl delete pod <이전 파드>`)로 그때는 넘겼지만, **근본 조치는 `strategy: Recreate`** (7절) — 자동화(CD)에서는 사람이 매번 지워줄 수 없다 |
| `.env`가 이미지에 그대로 들어가 Docker Hub까지 올라감 | `.dockerignore` 없이 `COPY . .` | 3절의 `.dockerignore`를 반드시 같이 커밋한다. 빌드 뒤 `docker run --rm <이미지> ls /app`로 직접 확인한다. 이미 올라갔다면 관련 비밀값(DB 비밀번호·JWT 시크릿 등)을 교체(rotate)한다 |
